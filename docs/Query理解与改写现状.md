# Query 理解与改写：现状与暂缓决策

本文如实记录 rag-kb 在「Query 理解与改写」环节的现状：**已实现的只有多轮对话场景的
指代消解**；扩写、重写、HYDE、意图识别均为**评估后明确暂缓**的决策（不是遗漏），
每项的理由与启动条件都记录在 `TODOS.md`，此处汇总指路。

## 已实现：指代消解（2026-07-15，随多轮对话记忆上线）

- **代码**：`DeepSeekCoreferenceResolver`（`backend/.../ragcore/conversation/impl/`），
  由 `ConversationMemoryOrchestrator.prepareContext()` 在检索前调用；
- **行为**：仅当会话存在历史消息时，调 LLM 把当前问题的代词/省略补全为独立完整问题
  （如"那它过了还能退吗"→"重疾险过了还能退吗"）；prompt 明确只做指代消解，**不改写
  技术术语/错误码/配置项**；调用失败或超时 fail-open，直接用原始问题继续检索；
- 详见[总体架构](architecture.md)决策 5 与多轮对话记忆的设计文档。

## 保持关闭：Query 重写（rewrite）

`QueryRequest.rewrite` 字段是预留空壳，**首期固定关闭**（理由写在
`QueryController.QueryRequest` 注释里）：本项目高价值查询恰是 `NullPointerException`、
配置 key 这类必须逐字精确的 token（BM25 已给 `symbol_names`/`config_keys`/`error_codes`
7-8 倍权重），LLM"润色"可能把精确匹配改没——技术文档场景下重写的风险大于收益
（[总体架构](architecture.md)决策 3）。

## 评估后暂缓（详见 `TODOS.md` 对应条目）

| 方向 | 一句话结论 | 启动条件 |
|---|---|---|
| **Query 扩写**（同义词多路检索） | bge-m3 向量腿天然覆盖大部分同义词漂移，剩余收益集中在领域黑话；无证据前属预防性堆功能 | 先对 v2 评估集约 12 道 Recall@5 失败题做错误归因，确认失败原因确实是同义词错配 |
| **HYDE**（假设文档检索） | 对短查询/黑话查询的向量召回有针对性提升，但每次查询多一次 LLM 调用 | 先用评估集分"短查询/长查询"两组看 Recall 差异，有证据再做 |
| **查询意图识别** | 是"RRF 动态权重"等一系列优化的前提，但单一技术问答场景下意图类别可能不足以支撑收益 | 先等动态权重条目的分类误差分析给出证据；若启动，从规则/关键词路线起步 |
| **RRF 动态权重**（按查询类型调两路权重） | 固定等权已跑通且有 0.904 的基线，材料建议"先做分类误差分析再决定" | 用 v2 评估集把 query 分成"关键词主导/语义主导"两类看 Recall 差异 |

这些条目共同的方法论：**先归因、有证据、再动手**——不在没有失败案例支撑的情况下
预防性地增加检索链路复杂度（每一项都有延迟/成本/维护代价）。
