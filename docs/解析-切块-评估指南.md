# 解析、切块与评估指南

本文是 rag-kb「文档解析 → 结构感知切块 → 切分质量评估」三个环节的**权威入口文档**。
每节先讲当前实现与能力边界，再指向对应的详细文档和工具。

链路全景：

```text
上传 → 解析（backend Parser + parser-gateway/deepdoc）
     → 切块（TechnicalChunker V3，结构感知）
     → 索引（Elasticsearch BM25 + kNN，chunk metadata dynamic 透传）
     → 检索问答（RRF + Rerank + SSE）
     → 评估（eval/ 离线评测：Recall@k / MRR / 拒答 F1）
```

---

## 一、解析（Parsing）

### 当前实现

- **backend `DocumentParserFactory`**：Markdown、代码、JSON/YAML/XML、DOCX、PPTX、文本 PDF、字幕等直接在 Java 侧解析；
- **parser-gateway（Python）**：扫描 PDF / 图片走 OCR，音视频走 ASR；
- **deepdoc 集成**（移植自 RAGFlow deepdoc，Apache 2.0，见 `parser-gateway/app/deepdoc/LICENSE_THIRD_PARTY`）：
  - **版面分析**（LayoutRecognizer）：解决多栏扫描文档被按行交叉拼接的问题；
  - **表格结构识别**（TSR + R/C 标注算法）：解决无边框表格行列错配的问题。

### 已知限制（详见 `TODOS.md` 的 deepdoc 后续项）

- 文本型 PDF（无需 OCR 的多栏 PDF）仍走 PyMuPDF 原生提取，多栏交叉问题未修；
- 印章压字无解决方案（四个参考项目均未解决）；
- deepdoc 效果仅用合成图片验证过，真实扫描件样本待验收；
- XLSX 与含图 DOCX 不被 `DocumentParserFactory` 支持，评估语料需先用
  `eval/scripts/xlsx_to_md.py` / `docx_to_md.py` 预处理（见第三节）。

## 二、切块（Chunking）—— V3 结构感知五招式

`TechnicalChunker`（`backend/.../ragcore/chunk/impl/`）在 2026-07-14 完成 V3 升级
（PR #13），实现五项结构感知技术：

| # | 招式 | 实现 |
|---|---|---|
| 1 | 多风格文档层级识别 | `HeadingStyle` 枚举：CN_FORMAL（编/部分→章→节→条→(一)）、CN_NUMERIC（1./1.1/1.1.1）、CN_INFORMAL、EN 四套模式组，`detectDominant()` 按命中数自动选主风格，未命中则优雅降级 |
| 2 | 递归多级级联切分 | 超长结构单元按 结构层级 → 空行段落 → 句子(+overlap) 三级递归降级（`recursiveSplit`），任何一级失败自动降到下一级 |
| 3 | 表格专用切块 | `chunkTableSection`：大表格按行分组，**每组重复表头**，保证跨 chunk 检索时表头语境不丢；仅超长表头无数据行时也不丢块 |
| 4 | 智能重叠 | overlap 起点对齐句子边界（不从半句开始），默认 160/1200 ≈ 13% 比例，已由回归测试锁定 |
| 5 | 丰富 chunk 元数据 | `enrichMetadata()` 写入 `sectionPath` / `contentType` / `isKeyClause` / `prevChunkId` / `nextChunkId`；因 ES 索引对 `metadata` 做 `dynamic:true` 透传，**零 schema / 索引代码改动** |

**明确不在 V3 范围内**（记录于 `TODOS.md`）：ML 分类器兜底（层级识别目前纯规则）、检索侧对 prevChunkId/nextChunkId 的消费（上下文扩展）。

### 切块行为快速验证

## 三、评估（Evaluation）

### 方法论

> 业内共识：**没有评估集的切分优化都是自嗨。**

量化切分质量的标准做法是构造 QA 评估集跑检索召回：

1. 选一批代表性文档；
2. 人工出题 + 标注 ground-truth chunk（答案应来自哪个 chunk）；
3. 用当前切分方案建库，对每题检索 top-k，看 ground-truth 是否被找到；
4. 换切分策略重复跑，横向对比。

核心指标（由 `eval/metrics.py` 计算）：

- **Recall@k**：可回答题中，前 k 个检索结果命中任一 ground-truth chunk 的题目占比——最直接反映切分是否合理；
- **MRR**：答案 chunk 首次命中排名的倒数平均——反映排序质量；
- **拒答精确率/召回率/F1**：期望拒答题（无依据/越界）是否被正确拒答。

### 完整评测工作流

```bash
# ① 语料预处理（仅 XLSX / 含图 DOCX 需要）
python3 eval/scripts/xlsx_to_md.py in.xlsx out.md
python3 eval/scripts/docx_to_md.py in.docx out.md

# ② dump corpus 索引（真实跑 V3 解析+切块）—— 详细步骤见 eval/datasets/README.md
java -cp ... EvalCorpusIndexer eval/datasets/corpus/<主题> eval/datasets/corpus-index.jsonl

# ③ 生成 QA 骨架 → 业务专家复核标注
python3 eval/scripts/build_qa_set.py

# ④ 生成检索预测
#    mock 模式：predicted = ground truth，仅验证 pipeline（指标恒为 100%，无评测意义）
python3 eval/scripts/generate-predictions.py --mode mock --output eval/predictions/xxx.jsonl
#    api 模式：调后端真实检索（前置条件见下方「真实评测待办」）
python3 eval/scripts/generate-predictions.py --mode api --api-url http://localhost:8080 ...

# ⑤ 出报告
python3 -m eval.runner \
  --ground-truth eval/datasets/eval-set-2026Q3.jsonl \
  --predicted    eval/predictions/xxx.jsonl \
  --meta chunker=technical-chunker@v3 \
  --output-md eval/reports/eval-xxx.md
```

一键跑 mock 全流程：`bash eval/run-quick-eval.sh`。

**基线跑法**（复现）：`eval/scripts/EvalRetrievalRunner.java` —— 把 `corpus-index.jsonl`
的 885 个 V3 真实切块连同真实 bge-m3 向量经产品 `ElasticsearchChunkIndex` 写入独立
评测索引 `rag_chunks_eval_v3`，再逐题调用产品 `HybridRetriever`（BM25+kNN+RRF+rerank）。
chunk_id 与 ground truth 同源，无映射误差。命令见该文件头部注释与 datasets/README。

**核心实证**：同一套检索系统，在机器骨架集上 Recall@5 仅 26.4%，换成人工标注 v2 集后
91.2%——评估集质量决定评测有效性；此前的低分是评估集假阴性，不是检索能力问题。
详细解读（含分桶短板与方法论注记）见 v2 报告尾部。

**后续评测待办**（按预期收益排序）：

1. **拒答阈值校准（产品端真实缺陷）**：`MIN_RRF_SCORE=0.01` 三轮实测拒答 F1 均为 0——混合召回总能凑出候选分数，需引入分数校准或相关性下限；
2. 业务专家对 v2 做一轮独立盲标复核（30% 抽样、Jaccard ≥ 0.8），补齐验收门 6 的严格形态（当前为 AI 单标注人+锚点复核）；
3. ES 加中文分析器（IK / smartcn）+ heading_path 参与 BM25 召回，观察 module/config 短板类（Recall@5 0.82-0.83）能否抬升；
4. 检出 `1fc29ab`（V0 切分）在同一 v2 集组合下重跑，得到切分策略的真实对比。
