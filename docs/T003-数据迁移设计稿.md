## 2. V005__add_ingestion_job.sql（设计稿）

```sql
-- V005: 新增摄取任务表与文档对象存储字段
-- 前置: T002 IngestionStatus 枚举已冻结

-- 2.1 文档表：新增对象存储定位与错误/重试字段
ALTER TABLE document
    ADD COLUMN object_storage_path VARCHAR(1000),        -- MinIO/S3 对象路径
    ADD COLUMN retry_count        INTEGER NOT NULL DEFAULT 0,
    ADD COLUMN last_error         TEXT,
    ADD COLUMN last_error_at      TIMESTAMPTZ;

COMMENT ON COLUMN document.object_storage_path IS '对象存储中原始文件的路径，格式: org/{orgId}/kb/{kbId}/{filename}';
COMMENT ON COLUMN document.retry_count IS '已重试次数，非空默认 0';
COMMENT ON COLUMN document.last_error IS '最近一次失败的错误信息';
COMMENT ON COLUMN document.last_error_at IS '最近一次失败的时间';

-- 2.2 摄取任务表
CREATE TABLE ingestion_job (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    document_id     UUID         NOT NULL REFERENCES document(id) ON DELETE CASCADE,
    org_id          UUID         NOT NULL REFERENCES organization(id),
    kb_id           UUID         NOT NULL REFERENCES knowledge_base(id),
    status          VARCHAR(30)  NOT NULL DEFAULT 'QUEUED',  -- IngestionStatus 枚举值
    attempt         INTEGER      NOT NULL DEFAULT 0,         -- 当前尝试次数，从 0 起
    max_attempts    INTEGER      NOT NULL DEFAULT 3,
    payload         JSONB,                                    -- 灵活扩展字段（解析参数、模型版本等）
    error_message   TEXT,
    started_at      TIMESTAMPTZ,
    finished_at     TIMESTAMPTZ,
    created_at      TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ  NOT NULL DEFAULT now()
);

-- 索引
CREATE INDEX idx_ingestion_job_document_id ON ingestion_job(document_id);
CREATE INDEX idx_ingestion_job_org_id      ON ingestion_job(org_id);
CREATE INDEX idx_ingestion_job_status      ON ingestion_job(status);
-- 按状态和创建时间查询待处理任务（Worker 轮询用）
CREATE INDEX idx_ingestion_job_pending     ON ingestion_job(status, created_at)
    WHERE status IN ('QUEUED', 'RETRYABLE_FAILED');

COMMENT ON TABLE ingestion_job IS '文档摄取异步任务表';
COMMENT ON COLUMN ingestion_job.status IS 'IngestionStatus: QUEUED/PARSING/CHUNKING/EMBEDDING/INDEXING/READY/FAILED/DELETING';
COMMENT ON COLUMN ingestion_job.attempt IS '当前尝试次数';
COMMENT ON COLUMN ingestion_job.payload IS 'JSON: 解析选项、chunk 参数、embedding 模型版本等';
```

## 3. 设计决策

### 3.1 为什么用 database 轮询而不是消息队列

架构设计文档第 3 节已决策：「首期足够轻量，具备幂等、可重试、可观测」。Worker 通过 `idx_ingestion_job_pending` 索引高效查询 `QUEUED` 和 `RETRYABLE_FAILED` 状态的任务。

### 3.2 幂等性保证

1. 同一 `document_id` 在同一时间只应有一个 `QUEUED`/`RUNNING` 状态的任务。
2. 重试时：先按 `document_id` 删除 ES 中的旧 chunks，再重新写入，最后标记 `READY`。
3. 使用 `UPDATE ... WHERE status = 'QUEUED'` 的原子方式领取任务（`SELECT ... FOR UPDATE SKIP LOCKED`）。

### 3.3 状态机

已由 GPT-5.6 的 T002 在 `IngestionStateMachine.java` 中实现：
- QUEUED → PARSING → CHUNKING → EMBEDDING → INDEXING → READY
- 任一步骤可 → FAILED → QUEUED（重试）或 DELETING
- READY → QUEUED（重新摄取）或 DELETING
- FAILED → QUEUED（重试）或 DELETING
- DELETING 为终态，不可迁移

### 3.4 与旧字段的关系

- `document.ragflow_doc_id`：保留，不删除，不新增引用。历史上传的文档如果通过 RAGFlow 导入的，该字段仍有值。
- `document.status` 已有 `UPLOADING/PARSING/READY/FAILED`，与 `IngestionStatus` 重叠。**建议**：对应关系为 `QUEUED→UPLOADING, PARSING→PARSING, CHUNKING+EMBEDDING+INDEXING→PARSING（简化）, READY→READY, FAILED→FAILED, DELETING→新状态`。避免双写不一致，Worker 更新 `document.status` 时统一使用 IngestionStatus 到旧 status 的映射。
