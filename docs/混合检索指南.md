# 检索召回·混合检索指南

本文说明 rag-kb 混合检索环节的实现结构、关键参数与实验数字来源。

## 实现结构

```text
用户问题（经指代消解，见 Query理解与改写现状.md）
  └─ HybridRetriever（编排）
       ├─ ElasticsearchHybridCandidateSource：ES 原生 BM25 / kNN 双路召回 DSL
       ├─ RrfFusion：倒数排名融合，两路各 1/(60+rank) 等权相加
       ├─ 可选 Rerank（见 重排与检索优化指南.md）
       └─ 拒答判定（MIN_RERANK_SCORE 门槛，见 重排与检索优化指南.md）
```

- **代码**：`HybridRetriever.java` / `ElasticsearchHybridCandidateSource.java` /
  `RrfFusion.java` / `ElasticsearchChunkIndex.java`（`rag_chunks_v1` mapping 与 Bulk
  Upsert）/ `RetrievalOptions.java`（均在 `backend/.../ragcore/retrieval|index/`）；
- **BM25 侧字段加权**：`symbol_names` / `config_keys` / `error_codes` 等技术标识字段
  7-8 倍权重，保证类名/错误码/配置 key 这类必须逐字精确的查询优先走关键词精确召回
  （这也是 Query Rewrite 保持关闭的原因，见[总体架构](architecture.md)决策 3）；
- **多租户隔离**：ES 查询由服务端强制注入 `org_id`/`kb_id` 过滤，跨组织按资源不存在
  处理（[总体架构](architecture.md)决策 4，自动化测试为发布门禁）。

## 关键参数与数字来源

| 参数/数字 | 值 | 怎么来的 |
|---|---|---|
| 生产默认候选池 `candidateLimit` | 50 | 2026-07-15 用 150 题 v2 评估集实测 N∈{10,20,30,50}：N 降到 10 时 Recall@5 掉 5.6 个百分点、只换回约 430ms（median），性价比不划算，**默认 50 不下调**。报告 `eval/reports/candidate-pool-size-tuning-20260715.md` |
| 最终保留 `resultLimit` | 8 | 进生成 prompt / 作为引用来源的片段上限 |
| RRF `rank_constant` | 60 | 业界常用默认值；动态权重（按查询类型调 BM25/向量权重）已评估暂缓，见 `TODOS.md`「RRF 融合动态权重」 |
| **权威基线 Recall@1/5/10 = 0.816/0.904/0.912，MRR = 0.849** | — | 150 题人工标注 v2 评估集 × 本页完整链路（含拒答门槛）实测，报告 `eval/reports/eval-v2-calibrated-20260714.md`；评测方法论与"机器骨架集 26.4% vs 人工标注集 91.2%"的实证见[评估指南](评估指南.md) |

## 降级行为

- Embedding 不可用 → BM25-only（见 [Embedding指南](Embedding指南.md)）；
- Rerank 不可用 → 直接返回 RRF 排序结果（见[重排与检索优化指南](重排与检索优化指南.md)）；
- 两类降级都写入审计标记（`embedding_fallback`/`rerank_fallback`）并告警。
