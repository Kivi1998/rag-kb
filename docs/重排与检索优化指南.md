# 重排（Rerank）与检索优化指南

本文说明 rag-kb 重排环节的实现、拒答阈值的校准过程（数字怎么来的）与已知机制性局限。

## 当前实现

- **接口**：`RerankerClient`（`backend/.../ragcore/rerank/RerankerClient.java`）；
- **实现**：`OpenAiCompatibleRerankerClient`（Cross-Encoder 兼容协议）；
- **已验证基线模型**：硅基流动在线 API 的 `BAAI/bge-reranker-v2-m3`；代码使用兼容 HTTP 客户端，不把供应商硬编码为硅基流动；
- **位置**：`HybridRetriever` 在 RRF 融合后对候选片段重排（可选，`RetrievalOptions.rerank`）；
- **降级**：Rerank 服务不可用时直接返回 RRF 排序结果，记录 `rerank_fallback` 审计标记并
  告警，不中断检索。

## 拒答阈值 `MIN_RERANK_SCORE=0.06`：校准过程（不是拍脑袋定的）

**原始问题**：最早只有 `MIN_RRF_SCORE=0.01` 一道门槛，三轮实测拒答 F1 均为 0——RRF
分数分母含 `rank_constant=60`，任何 top-1 候选几乎必然超过该阈值，从未真正拦截过任何
拒答题。

**实验方法**（完整记录见 `eval/reports/refusal-threshold-calibration-20260714.md`，
复现脚本 `eval/scripts/analyze_refusal_threshold.py`）：

1. 在 150 题人工标注评估集上跑真实检索，把每题 top-1 候选的 rerank 分数作为诊断字段
   一起输出；
2. 按人工标注分成"应拒答"（25 道）与"应回答"（125 道）两组，观察分数分布差异；
3. 对候选阈值 t（0→1，步长 0.005）逐个计算"分数 < t 就拒答"规则的精确率/召回率/F1，
   选 F1 最优点。

**结果**：t=0.06 时 F1=0.564 全局最优（从 0 提升），命中 11/25 道拒答题，代价是误伤
3/125 道应答题（Recall@5/MRR 各降 0.008，权衡记录在报告里）。

**已知机制性局限（不是调参能解决的）**：按拒答子类型细分，t=0.06 只对
LOW_CONFIDENCE（4/4）和 OUT_OF_SCOPE（10 中 9）有效；**NO_RETRIEVAL**（主题相关但
具体事实缺失，8 道题 rerank 分数 0.178–0.921）与 **SAFETY**（内容合规）两类分数普遍
很高——reranker 衡量的是"主题相关性"而非"该问题的具体答案是否存在"。NO_RETRIEVAL
已由生成阶段事实核验补上（[总体架构](architecture.md)决策 8，8/8 命中）；SAFETY 仍无
方案（需独立内容安全分类器，见 `TODOS.md`）。

## 阈值扩展到全部候选片段（2026-07-16）

`MIN_RERANK_SCORE` 检查从只看排名第一的片段，扩展到全部候选片段——排名靠后但分数
不达标的片段直接过滤，不进生成 prompt 也不出现在参考来源里（[总体架构](architecture.md)
决策 9）。注意：生成后自检（`AnswerSelfChecker`）复用这个阈值的效果**经真实验证不达
预期**（只能拦"完全文不对题"的编造，对"部分相关的编造"基本拦不住，4/6 命中），阈值
需要为自检场景专门校准，见 `TODOS.md`「自检机制仍待解决」。
